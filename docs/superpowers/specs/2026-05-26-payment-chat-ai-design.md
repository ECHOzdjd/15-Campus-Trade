# 校园交易支付、图片消息与 AI 增强设计

日期：2026-05-26

## 目标

在现有校园二手交易流程上补齐三类能力：

1. 支付流程：明确买家付款后钱流向哪里、订单如何流转、卖家什么时候能收到钱。
2. 违约处理：明确买家下单后不付款、面交后不确认、双方产生争议时系统如何处理。
3. 对话增强：聊天页支持发送图片，并把关键订单动作以系统消息形式沉淀在对话中。
4. AI 增强：加入实用型 AI 功能，让项目不止是基础 CRUD。

## 当前系统边界

当前系统已经具备商品、订单、收藏、对话、图片上传和 SSE 实时消息基础。订单状态较简单，主要围绕 `pending / confirmed / cancelled`，还没有钱包、支付流水、托管金额、退款和争议状态。对话消息目前按文本消息处理，上传接口可复用到图片消息。

本设计不接真实微信、支付宝或银行卡支付。原因是课程项目无法稳定解决真实商户资质、回调验签、合规、退款结算和敏感资金监管。采用模拟钱包可以完整演示业务闭环，并保持实现可控。

## 方案对比

### 方案 A：线下支付记录

买卖双方线下面交，平台只记录“已付款 / 未付款 / 有争议”。实现最简单，但平台无法控制资金，不能真正解决“买家拿货后不付钱”的问题。

### 方案 B：真实支付接入

接入真实支付渠道，买家付款进入商户账户，再结算给卖家。真实性最高，但开发和合规成本远超当前项目规模。

### 方案 C：模拟担保支付

平台内置校园余额。买家先把钱付到平台托管账户，确认面交后平台放款给卖家。可以展示付款、托管、放款、退款、争议和余额流水。

推荐采用方案 C。

## 核心业务规则

### 钱流向

资金流向固定为：

买家钱包余额 -> 平台托管账户 -> 卖家钱包余额

订单完成前，卖家不能直接收到钱。订单退款时，托管金额退回买家钱包。

### 买家不付款

买家点击购买后，订单进入待付款状态，商品进入锁定状态。买家需要在限定时间内支付。建议第一期设置为 30 分钟。

如果超时未支付：

- 订单自动取消。
- 商品恢复在售。
- 聊天中生成系统消息：“订单超时未付款，商品已恢复在售。”

这能解决“买家占着商品但不付款”的问题。

### 买家面交后不确认

系统规则要求：卖家只应在订单状态为“已付款到托管”后再面交。

如果买家已付款到托管但面交后不确认：

- 卖家可以提交“申请放款”。
- 系统通知买家在 24 小时内处理。
- 第一版采用模拟仲裁处理，后续可加入超时自动放款。

如果买家绕过平台、未托管付款就拿走商品，系统无法保证资金，只能支持举报和证据留存。因此 UI 必须明确提示卖家：“未显示已托管付款前，不建议交付商品。”

## 订单状态设计

建议扩展订单状态：

- `pending_payment`：待付款，商品已锁定。
- `paid_escrow`：买家已付款，资金在平台托管。
- `meeting_confirmed`：一方已确认面交，等待另一方确认。
- `completed`：交易完成，资金已放款给卖家。
- `cancelled`：订单取消，商品恢复在售。
- `disputed`：争议中，暂停放款和退款。
- `refunded`：已退款给买家。

状态流转：

1. 买家下单：`pending_payment`
2. 买家支付：`paid_escrow`
3. 买家或卖家确认面交：`meeting_confirmed`
4. 双方确认：`completed`
5. 待付款超时或买家主动取消：`cancelled`
6. 任一方发起争议：`disputed`
7. 争议判定退款：`refunded`
8. 争议判定放款：`completed`

## 数据模型设计

### wallets

记录用户钱包余额。

- `id`
- `user_id`
- `balance`
- `frozen_balance`
- `created_at`
- `updated_at`

第一版可在注册用户或运行 schema guard 时自动创建钱包，并给种子用户初始余额。

### wallet_transactions

记录钱包流水。

- `id`
- `user_id`
- `order_id`
- `type`：`recharge | escrow_pay | escrow_release | refund | adjustment`
- `amount`
- `direction`：`in | out`
- `balance_after`
- `note`
- `created_at`

### payment_escrows

记录订单托管资金。

- `id`
- `order_id`
- `buyer_id`
- `seller_id`
- `amount`
- `status`：`held | released | refunded | disputed`
- `paid_at`
- `released_at`
- `refunded_at`

### disputes

记录争议。

- `id`
- `order_id`
- `opened_by`
- `reason`
- `status`：`open | seller_responded | resolved_refund | resolved_release`
- `resolution_note`
- `created_at`
- `resolved_at`

## API 设计

### 钱包

- `GET /api/wallet`：获取当前用户余额和最近流水。
- `POST /api/wallet/recharge`：模拟充值，仅开发演示使用。

### 支付

- `POST /api/orders/:id/pay`：买家支付到托管。
- `POST /api/orders/:id/confirm-received`：买家确认收到商品。
- `POST /api/orders/:id/confirm-handoff`：卖家确认完成面交。
- `POST /api/orders/:id/request-release`：卖家申请放款。
- `POST /api/orders/:id/cancel`：取消未支付订单。

### 争议

- `POST /api/orders/:id/disputes`：发起争议。
- `POST /api/disputes/:id/respond`：另一方回应争议。
- `POST /api/disputes/:id/resolve`：模拟仲裁，退款或放款。

### 图片消息

- `POST /api/upload/image`：继续复用现有上传接口。
- `POST /api/conversations/:id/messages`：扩展为支持 `type` 和 `content`。

请求示例：

```json
{
  "type": "image",
  "content": "/uploads/chat_123.png",
  "metadata": {
    "filename": "proof.png"
  }
}
```

## 聊天页设计

聊天页增加三类消息：

- 文本消息：当前已有能力。
- 图片消息：显示缩略图，点击打开预览。
- 系统消息：居中灰色提示，用于订单动作。

系统消息示例：

- “买家已付款到平台托管。”
- “卖家确认已完成面交。”
- “买家发起退款争议。”
- “平台已将托管金额放款给卖家。”

图片发送流程：

1. 用户点击图片按钮。
2. 前端调用上传接口。
3. 上传成功后发送 `image` 类型消息。
4. SSE 推送给对方。
5. 对方聊天页实时出现图片。

## 前端页面调整

### 商品详情页

- “立即购买”改为创建待付款订单。
- 显示提示：下单后需要先付款到平台托管，再与卖家面交。

### 订单详情页

根据状态显示不同操作：

- `pending_payment`：买家显示“立即支付”，卖家显示“等待买家付款”。
- `paid_escrow`：显示“已付款到托管”，双方可进入消息页约面交。
- `meeting_confirmed`：显示对方确认情况。
- `completed`：显示“已放款给卖家”。
- `disputed`：显示争议信息。

### 钱包页

新增“我的钱包”页面：

- 当前余额
- 模拟充值
- 交易流水
- 冻结/托管说明

### 争议页

第一版可放在订单详情内，不单独做复杂页面：

- 发起争议表单
- 原因文本
- 图片证据
- 处理结果

## AI 功能设计

AI 功能采用可插拔服务。第一版保留 mock/rule-based 模式，后续通过环境变量接入真实模型。

建议接口：

- `POST /api/ai/product-draft`
- `POST /api/ai/price-suggestion`
- `POST /api/ai/risk-check`

### AI 商品发布助手

输入：

- 商品标题草稿
- 简短描述
- 分类
- 成色

输出：

- 更完整的标题
- 商品描述
- 分类建议
- 成色描述建议

### AI 定价建议

输入：

- 分类
- 成色
- 原价或购入价
- 描述

输出：

- 快速成交价
- 合理成交价
- 偏高展示价
- 简短理由

### AI 风险提示

对聊天内容做轻量风险检查。第一版可以先用关键词规则实现，不依赖外部 API。

风险词包括：

- “先转账”
- “不走平台”
- “押金”
- “校外”
- “私下付款”
- “扫码付款”

触发后在聊天页显示提示：

“这条消息可能涉及平台外付款或高风险交易，建议确认订单已付款到托管后再面交。”

## 实施顺序

第一阶段：支付主链路

- 钱包表、流水表、托管表。
- 待付款、付款到托管、确认面交、放款、退款。
- 订单详情页状态和按钮。

第二阶段：图片消息

- 扩展消息类型。
- 聊天图片上传、预览、SSE 推送。
- 系统消息。

第三阶段：争议处理

- 发起争议。
- 上传证据。
- 模拟仲裁。
- 退款或放款。

第四阶段：AI 增强

- AI 发布助手。
- AI 定价建议。
- AI 风险提示。
- 默认 mock 模式，真实模型通过配置启用。

## 验收标准

- 买家下单后不会直接完成订单，必须先支付到托管。
- 未付款订单不会永久占用商品。
- 托管付款后，卖家能明确看到“已付款到托管”再面交。
- 双方确认后，卖家钱包余额增加，买家托管资金扣除。
- 退款后，买家余额恢复，卖家不收到钱。
- 聊天页可以发送和实时接收图片。
- 订单关键动作会在聊天中出现系统消息。
- AI 发布助手、定价建议、风险提示至少有 mock 模式可用。

## 非目标

- 不接真实微信、支付宝、银行卡。
- 不做真实人工客服后台。
- 不做复杂信用评分和自动处罚。
- 不做真实法律仲裁。
